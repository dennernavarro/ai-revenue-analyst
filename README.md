# AI Revenue Analyst

[![CI](https://github.com/dennernavarro/ai-revenue-analyst/actions/workflows/ci.yml/badge.svg)](https://github.com/dennernavarro/ai-revenue-analyst/actions/workflows/ci.yml)

An open-source AI revenue analyst for short-term rentals and small hotels.
Ask questions about occupancy, ADR, RevPAR, booking pace and rates in plain
language; run pricing reviews with human approval; or integrate it through a
REST API. It ships with a web dashboard (occupancy calendar, room categories,
chat with the analyst), a realistic mock property-management system (PMS) and
simulated booking data, and is built so a real PMS can be plugged in later
through a single interface.

Built with LangChain, LangGraph, Deep Agents, FastAPI and (optionally)
LangSmith.

## Requirements

- Python 3.11+
- [uv](https://docs.astral.sh/uv/)
- An LLM API key — by default an [OpenRouter](https://openrouter.ai/keys) key
- Node 20+ only for frontend development (Docker builds the UI for you)

## Install

```bash
git clone https://github.com/dennernavarro/ai-revenue-analyst.git
cd ai-revenue-analyst
uv sync
cp .env.example .env   # then put your OPENROUTER_API_KEY in .env
```

Check everything works (no API key needed for the tests):

```bash
uv run pytest
```

## Usage

### Web dashboard

```bash
docker compose up --build
```

Then open **http://localhost:8000/ui** — property switcher, KPI row, the
month-by-month occupancy calendar (nightly rate and nights sold per day),
room-category occupancy, and the chat panel with visible tool activity and
approve/decline cards for pricing reviews. The **Deep** toggle in the chat
header switches to the deep agent: the panel turns amber, suggestions become
portfolio-sized missions, and you watch it plan and delegate to specialist
subagents through delegation cards.

For frontend development, run the API (`uv run uvicorn
revenue_analyst.api:create_app --factory`) and, in `frontend/`,
`npm install && npm run dev` — Vite serves http://localhost:5173 with a proxy
to the API. `npm run build` produces `frontend/dist`, which the API serves at
`/ui` whenever it exists.

### Chat with the analyst (terminal)

```bash
uv run python -m revenue_analyst.cli
```

```text
you> How did Seaside Villa perform in August 2026?
  ⚙ get_performance({'property_id': 'seaside-villa', ...})
analyst> Occupancy was 77.4%, ADR $510, RevPAR $394.84 ...
```

Every number comes from deterministic tools — the model never invents
figures. Conversations persist in `.state/` across restarts; use
`--thread <id>` for separate conversations, `--once "question"` for a single
question, and `--deep` for the deep-agent variant: its lead holds no data
tools, so it must plan (`write_todos`) and delegate (`task()`) to specialist
subagents — watch the ⚙ trace to see the delegation happen on big
multi-property tasks.

### Pricing review with human approval

```bash
uv run python -m revenue_analyst.review mountain-cabins 2026-12-01 2027-01-01
```

If the window is pacing below target, the workflow proposes a rate adjustment
(bounded by a ±25% policy enforced in code) and pauses for your approval.
Approving publishes the new rates through the `RatePublisher` port — a write
port deliberately separate from data reading; the mock applies them in
memory, so a restart returns to the generated rates. Duplicate review
requests for the same window are deduplicated server-side, and a decision can
only be applied once. Set `RA_RATE_PUBLICATION=false` for record-only mode.

### REST API

```bash
uv run uvicorn revenue_analyst.api:create_app --factory --reload
```

Interactive docs at http://127.0.0.1:8000/docs.

| Endpoint | Description |
|---|---|
| `GET /properties` | List properties |
| `GET /properties/{id}/performance?start=&end=` | Occupancy, ADR, RevPAR, revenue (no LLM) |
| `GET /properties/{id}/pace?start=&end=` | Booking pace vs 30/60/90 days ago (no LLM) |
| `GET /properties/{id}/calendar?start=&end=` | Per-day rate, min-stay and nights sold (no LLM) |
| `GET /properties/{id}/room-types?start=&end=` | Categories with units, from-rate and occupancy (no LLM) |
| `POST /chat` | Talk to the agent; pass `conversation_id` to continue |
| `POST /reviews` | Start a pricing review (may pause for approval) |
| `POST /reviews/{id}/decision` | Approve or reject a pending review |

Date ranges are half-open: `end` is excluded.

### Docker

```bash
docker compose up --build
```

Builds a multi-stage image (uv-locked dependencies, slim runtime, non-root
user) and serves the API on port 8000. The `.env` file supplies the LLM key,
and conversation checkpoints live in a named volume, so chat memory survives
container restarts.

### Mock data

Three simulated properties (as of a simulated "today", 2026-11-01): a
single-unit beach villa, a 12-room city hotel and four mountain cabins — each
with its own seasonality, lead times and cancellation behavior. Data is
generated by simulating booking arrivals (not invented occupancy numbers), so
pace, gaps and revenue stay internally consistent. Regenerate it any time
(deterministic seeds):

```bash
uv run python scripts/generate_data.py
```

## Configuration

Everything is set via environment variables / `.env`:

| Variable | Default | Description |
|---|---|---|
| `OPENROUTER_API_KEY` | — | Key for the default model route |
| `RA_PMS_PROVIDER` | `mock` | Which PMS adapter backs the app (see `pms/factory.py`) |
| `RA_MODEL` | `openrouter:openai/gpt-4o-mini` | Any `openrouter:<vendor>/<model>`, `anthropic:<model>`, `ollama:<model>`, ... |
| `RA_DATA_DIR` | `data` | Where the mock datasets live |
| `RA_STATE_DIR` | `.state` | SQLite conversation checkpoints |
| `RA_RATE_PUBLICATION` | `true` | Approved reviews publish rates via the write port; `false` = record-only |
| `LANGSMITH_TRACING` + `LANGSMITH_API_KEY` | off | Optional tracing; everything works without it |

## How it works

```text
frontend/ (React dashboard, served at /ui)
        │
cli.py / review.py / api.py          ← entry points
        │
agents/  (chat agent · deep agent with subagents · pricing-review workflow)
        │
tools.py (read-only @tool) → analytics.py (pure calculations)
        │
pms/provider.py (read + write ports) → pms/factory.py → pms/mock.py → data/*.json
```

Design rules the codebase follows:

- Tools calculate, agents reason — KPIs come from tested pure functions.
- The PMS behind `PMSProvider` is replaceable: copy
  [pms/template.py](src/revenue_analyst/pms/template.py), fill in its TODOs,
  register it in `pms/factory.py`, and make it pass the same contract tests
  (`tests/test_pms_contract.py`) — then select it with `RA_PMS_PROVIDER`.
- Hard business constraints (rate bounds, approval gates) are enforced in
  code, outside the LLM.
- GET endpoints never touch the LLM; only `/chat` and `/reviews` do.

## Development

```bash
uv run pytest        # full suite, runs offline (agents tested with fake models)
uv run ruff check .  # lint
```

Behavioral evaluation (needs an LLM key; ground truth is computed from the
deterministic layer, so the dataset never drifts from the simulator):

```bash
uv run python -m revenue_analyst.evals              # local run + pass/fail report
uv run python -m revenue_analyst.evals --langsmith  # also log a LangSmith experiment
```

This project was built incrementally as a learning journey through modern
agent tooling — the stage-by-stage write-ups, including what hurt and what
each framework actually buys you, live in [docs/notes/](docs/notes/).
